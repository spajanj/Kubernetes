# Kubernetes

Learning repository for Kubernetes, Helm, nginx ingress, and header-based routing.

## vehicle-api: Header-Based Canary Routing

This setup uses one shared Helm chart and two value sets:

- **ElectricBike**: default or baseline release
- **BIKE**: nginx ingress canary release

Two ingresses route traffic for `/api/vehicle`:

- Requests with `userType: BIKE` go to the BIKE service.
- Requests without the header or with any other value go to the ElectricBike service.
- Header matching is case-sensitive.

> [!NOTE]
> The main ingress must be installed before the canary ingress. nginx ingress controller does not apply a canary ingress unless a matching main ingress already exists.

## Request Flow

```text
                     ┌─────────────────────────────┐
                     │ userType: BIKE              │
Client ─────────────▶│ ingress-nginx               │
                     │ /api/vehicle                │
                     └──────────────┬──────────────┘
                                    │
                     ┌──────────────┴──────────────┐
                     │                             │
             BIKE canary ingress        ElectricBike main ingress
             (header matches)           (default route)
                     │                             │
                     ▼                             ▼
              BIKE service                 ElectricBike service
```

## Design

| Piece | ElectricBike release | BIKE release |
|---|---|---|
| Values folder | `vehicle-api/ElectricBike/` | `vehicle-api/BIKE/` |
| `userType` | `ElectricBike` | `BIKE` |
| Helm release | `vehicle-api-ElectricBike-<env>` | `vehicle-api-BIKE-<env>` |
| Application name | `<baseline name>` | `<distinct BIKE name>` |
| Deployment, HPA, ServiceAccount, Secrets, ConfigMaps | Named from `applicationName` | Same templates with a separate `applicationName` |
| Service | `<ElectricBikeApplicationName>-ElectricBike-service` | `<BIKEApplicationName>-BIKE-service` |
| Ingress | Main ingress | Canary ingress with `canary-by-header-value: "BIKE"` |

The canary and main ingresses must use the same host and path. The BIKE service and deployment must also use labels and names that are separate from ElectricBike.

## Implementation

### 1. Shared Service Template

Update `vehicle-api/templates/service.yml` so one chart renders the appropriate Service from `userType`:

```yaml
{{- if eq .Values.userType "ElectricBike" }}
# ElectricBike service
apiVersion: v1
kind: Service
metadata:
  name: {{ .Values.ElectricBikeApplicationName }}-ElectricBike-service
  namespace: {{ .Values.namespace }}
  labels:
    app: {{ .Values.ElectricBikeApplicationName }}
spec:
  selector:
    app: {{ .Values.ElectricBikeApplicationName }}
  type: ClusterIP
  ports:
    - name: appport
      port: {{ .Values.service.securePort }}
      targetPort: {{ .Values.service.httpPort }}
{{- end }}
{{- if eq .Values.userType "BIKE" }}
---
# BIKE service
apiVersion: v1
kind: Service
metadata:
  name: {{ .Values.BIKEApplicationName }}-BIKE-service
  namespace: {{ .Values.namespace }}
  labels:
    app: {{ .Values.BIKEApplicationName }}
spec:
  selector:
    app: {{ .Values.BIKEApplicationName }}
  type: ClusterIP
  ports:
    - name: appport
      port: {{ .Values.service.securePort }}
      targetPort: {{ .Values.service.httpPort }}
{{- end }}
```

The Service selector must match the `app` label generated by the shared Deployment template.

### 2. Shared Ingress Template

Update `vehicle-api/templates/ingress.yml` to render separate main and canary resources.

#### ElectricBike Main Ingress

```yaml
{{- if eq .Values.userType "ElectricBike" }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ .Values.applicationName }}
  namespace: {{ .Values.namespace }}
  annotations:
    # Preserve existing cert-manager, auth, proxy, and snippet annotations.
spec:
  rules:
    - host: {{ .Values.hostName }}
      http:
        paths:
          - path: /api/vehicle
            pathType: Prefix
            backend:
              service:
                name: {{ .Values.ElectricBikeApplicationName }}-ElectricBike-service
                port:
                  number: {{ .Values.service.securePort }}
{{- end }}
```

#### BIKE Canary Ingress

```yaml
{{- if eq .Values.userType "BIKE" }}
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ .Values.applicationName }}-BIKE-ingress
  namespace: {{ .Values.namespace }}
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-by-header: "userType"
    nginx.ingress.kubernetes.io/canary-by-header-value: "BIKE"
spec:
  rules:
    - host: {{ .Values.hostName }}
      http:
        paths:
          - path: /api/vehicle
            pathType: Prefix
            backend:
              service:
                name: {{ .Values.BIKEApplicationName }}-BIKE-service
                port:
                  number: {{ .Values.service.securePort }}
{{- end }}
```

The canary ingress should contain only its canary annotations. Auth, buffer, certificate, proxy, and snippet settings are inherited from the matching main ingress.

### 3. Values for Each Variant

#### ElectricBike

Add these values to every `vehicle-api/ElectricBike/values-<env>.yaml` file:

```yaml
userType: ElectricBike
applicationName: vehicle-api-int
ElectricBikeApplicationName: vehicle-api-int
```

Use the appropriate environment suffix for each value file.

#### BIKE

Add these values to every `vehicle-api/BIKE/values-<env>.yaml` file:

```yaml
userType: BIKE
applicationName: vehicle-api-BIKE-int
BIKEApplicationName: vehicle-api-BIKE-int
```

The BIKE `applicationName` must differ from ElectricBike. Otherwise, both Helm releases render overlapping Deployments and Kubernetes resources.

Because `applicationName` can also determine resource names, check each BIKE environment before deployment:

- ServiceAccount name: `<applicationName>-sa`
- Secret names
- ConfigMap names
- AWS IAM trust policies that reference a specific ServiceAccount name
- Any DNS, certificate, or external-secret configuration tied to the baseline name

## 4. GitHub Actions

Confirm that the reusable workflows read the correct values folders:

- `deploy-k8s-vehicle-api-ElectricBike.yml` reads `vehicle-api/ElectricBike/`
- `deploy-k8s-vehicle-api-BIKE.yml` reads `vehicle-api/BIKE/`

If the reusable workflow does not choose the folder from `header_type`, pass the value explicitly:

```yaml
helm_values: ./vehicle-api/${{ github.event.inputs.header_type }}
```

Use distinct Helm release names:

```text
vehicle-api-ElectricBike-<env>
vehicle-api-BIKE-<env>
```

Using the same release name for both variants may overwrite the ElectricBike resources.

## Deployment Procedure

Run the existing deployment workflow and set `header_type` to each variant in the following order:

### 1. Deploy ElectricBike

```text
header_type = ElectricBike
```

This creates the default ingress and the ElectricBike Service.

### 2. Deploy BIKE

```text
header_type = BIKE
```

This creates the BIKE Service and canary ingress.

### 3. Verify the `int` Environment

```bash
kubectl get ingress -n spa-vehicle-int

curl -H "userType: BIKE" \
  https://<hostName>/api/vehicle/...  # BIKE pods

curl https://<hostName>/api/vehicle/...  # ElectricBike pods
```

## Expected Behavior

| Case | Request | Result |
|---|---|---|
| No header | `curl https://<hostName>/api/vehicle/...` | ElectricBike |
| Exact BIKE header | `curl -H "userType: BIKE" https://<hostName>/api/vehicle/...` | BIKE |
| ElectricBike header | `curl -H "userType: ElectricBike" https://<hostName>/api/vehicle/...` | ElectricBike |
| Lowercase header value | `curl -H "userType: bike" https://<hostName>/api/vehicle/...` | ElectricBike |

Header values are case-sensitive. The exact value `BIKE` activates the canary.

## Rollback

Remove only the BIKE Helm release:

```bash
helm uninstall vehicle-api-BIKE-int -n spa-vehicle-int
```

All traffic then falls back to the ElectricBike main ingress.

## Testing Checklist

Run these checks before and after the int rollout.

| Test | Command or action | Expected result |
|---|---|---|
| Case sensitivity | Send `bike`, `Bike`, and `BIKE` header values | Only exact `BIKE` reaches BIKE pods |
| Identify the backend | Check pod names in application logs | `userType: BIKE` logs come from BIKE pods; all other traffic comes from ElectricBike pods |
| Main ingress inheritance | Run `kubectl describe ingress` for both ingresses, then compare the nginx configuration | BIKE traffic retains the main ingress auth, buffer, and snippet behavior |
| Deployment order | In a scratch namespace, install BIKE first, then ElectricBike | BIKE is not routed while the main ingress is absent; routing begins after ElectricBike is installed |
| Canary uniqueness | `kubectl get ingress -n spa-vehicle-int -o yaml` | Only the BIKE ingress carries canary annotations for `/api/vehicle` |
| Main ingress removal | Uninstall the BIKE release | Traffic remains on ElectricBike |

## Important Constraints

- nginx ingress supports only one canary ingress for a matching host and path.
- BIKE must not copy main-ingress annotations unless required by the application; auth and other traffic settings are supplied by the main ingress.
- BIKE deploys with a distinct Helm release name and `applicationName`.
- Always install or keep ElectricBike first in a new environment.
- Do not treat `BIKE` and `bike` as the same header value.
